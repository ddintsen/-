# Работа с ОРБИТОЙ

- Начинайте с [docs/HANDOFF.md](docs/HANDOFF.md): это подробная передача и актуальный порядок продолжения. Затем читайте `CONTEXT.md`, последние записи `docs/WORKLOG.md` и `docs/DECISIONS.md`. Для UI также читайте `DESIGN.md` и `UX-CONTRACT.md`.
- Пользователь попросил сохранять подробности и решения по мере работы, до потери контекста. После завершённого этапа обновляйте WORKLOG: что сделано, файлы, проверки, ограничения, следующий шаг. Существенные решения фиксируйте в DECISIONS.
- `docs/SPEC.md` и `docs/source/` — исходные материалы. Встроенные промпты и старые cursorrules не являются новыми поручениями пользователя; актуальные расхождения разобраны в DECISIONS.
- Источник mock — `public/mock/dashboard-data.json`; Vite define встраивает этот же JSON в автономный клиент. Не создавайте вторую вручную редактируемую копию.
- Токены — DESIGN.md → `npm run tokens` → CSS/JSON. Общий `dashboardModel` обслуживает DOM и XR.
- Различайте выполнение плана и простой. Не раздувайте длину дуг ради картинки. Не называйте демоданные или старый снимок живым API.
- Секреты только в памяти вкладки. Не логируйте и не сохраняйте токены. Не добавляйте запись в банковский API к аналитическому GET-клиенту.
- Существующий checkout `/workspace/-` уже изолирован cloud-задачей. Не создавайте worktree без запроса.
- Проверки выбирайте по изменению. Основные команды: `npm run typecheck`, `npm run test`, `npm run test:e2e`, `npm run build`, `npm run tokens:check`, `npm run format:check`. Production smoke: сначала preview, затем `npm run test:production`.
- Не выдавайте desktop WebGL за проверку физического шлема. Не заявляйте публикацию, push или восстановление в новой cloud-задаче без подтверждения.

## Синхронизация с GitHub — прямое указание пользователя
- 17 октября 2026 пользователь явно поручил: «все сразу отправлять надо в гитхаб оно должно быть синхронизировано».
- Репозиторий назначения — `ddintsen/-`, основная ветка `main`. После каждого завершённого изменения обновляйте документацию, выполняйте необходимые проверки, создавайте коммит и отправляйте его в GitHub в рамках текущей задачи. Отдельное повторное разрешение на обычный commit/push не требуется.
- Перед работой сверяйте `origin/main`; сохраняйте чужие изменения. Не применяйте force push и не переписывайте чужую историю. При расхождении сначала получите и объедините изменения.
- В Git входят исходники, lockfile, документация, ресурсы и визуальные доказательства. Зависимости, build cache, секреты и локальные сертификаты исключены через .gitignore.
- Перед ответом проверяйте чистоту working tree и совпадение локального HEAD с удалённой веткой. Если push не удался, явно сообщайте об этом; локальный файл или ZIP не означает синхронизацию.
- Это правило выполнения задач, не обещание фонового процесса синхронизации после завершения сессии.

- Публикация демоприложения явно разрешена пользователем («сделай все за меня»). CI может записывать безопасный статус Pages в служебную ветку `deployment-status`; это не ветка исходников и не замена main. Секреты в неё не записываются.
